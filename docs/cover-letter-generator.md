# Cover Letter Generator

## Context

Customers can upload resumes and manage search criteria, but had no way to turn a scraped job + a resume into a ready-to-send cover letter. This feature adds a "Generate a Cover Letter" form embedded directly in the Dashboard (not a separate route) that calls Claude to draft a cover letter, optionally matching the tone of a cover letter the customer has marked "Prime" or their 5 most recent ones ("All"). It closely mirrors the Resume feature's storage/SAS patterns, adding two new pieces: an Anthropic Claude integration in the C# backend (the Python scraper already calls Claude for job-posting enrichment, but there was no .NET client) and a "mark as Prime" toggle.

## Required dependency: `JobResult.BlobFileName`

`JobResult` had no field carrying the blob's filename, but the cover-letter form's job dropdown needs to submit a `jobBlobFileName`. `JobResult.BlobFileName` is set in code (not part of the scraper's JSON) — `JobSeekerController.GetJobs()` now assigns `job.BlobFileName = link.BlobFileName` after loading each job, so it flows through to the `GET /job-seeker/get-jobs` response for the frontend to use.

## Schema

### `CoverLetters` table
PartitionKey = `customerId`, RowKey = `coverLetterId` (a guid — this is also the blob's filename, with `.txt` appended).
- `CoverLetterName` — display name, e.g. "Cover letter 3 for Senior .NET Engineer"
- `ResumeId` — the resume used to generate it
- `JobId` — the scraper's job-posting id (`JobResult.Id`), stored for potential future use but **not** currently surfaced in `GET /cv/cover-letters`
- `IsPrime` — boolean, at most one `true` row per customer at a time
- `Timestamp` — used as `createdDate`

### Blob: container `cover-letters`, path `{customerId}/{coverLetterId}.txt`
Plain text, generated by Claude, written once (no edit/delete endpoint exists for cover letters today).

## "Prime" is explicitly user-marked, not "most recent"

A customer marks one cover letter as Prime via a star toggle on its card; `POST /cv/set-prime` clears any other Prime flag for that customer (sequential merge updates — not transactional, but self-healing: worst case is briefly 0 or 2 Primes if the second call fails, fixed on the next toggle) and sets the new one.

**Known limitation**: only the 3 most-recently-generated cover letters are ever shown as cards on the dashboard. If an older letter is flagged Prime but has aged out of the top-3, there's currently no way to see or change that from the dashboard. A future full cover-letters list page (mirroring Resume/Criteria) would resolve this.

The frontend's Prime/All radio-disable logic is deliberately simple and **not** Prime-aware — it only checks "does the customer have any cover letters at all" (the same signal already needed for the cards). A user can still select "Prime", submit, and get a 404 if they have letters but none flagged Prime. `POST /cv/generate` 404s for `"Prime"` whenever no row has `IsPrime=true`, and for `"All"` whenever the customer has zero cover letters.

## `.docx` resumes are rejected for this feature only

Claude's Messages API only natively accepts plain text and PDF document content — there's no `.docx` content type. `CoverLetterController.Generate` returns `400` if the selected resume's extension is `.docx`, with a message to re-upload as pdf/txt/md/html. `.docx` remains fully supported by the Resume feature itself (upload/download/delete) — this check is local to cover-letter generation.

## "All" style caps at 5

Sends the 5 most-recently-created cover letters (by `Timestamp` descending) as style examples, not literally all of them, to bound prompt size/cost/latency.

## Anthropic integration

`Operations/Ai/AnthropicClient.cs` is a focused, single-purpose typed `HttpClient` (not a generic SDK wrapper — there's exactly one consumer). Calls `POST https://api.anthropic.com/v1/messages` directly with `x-api-key`/`anthropic-version` headers — no Anthropic .NET package exists or is needed. Reads `anthropic-api-key` from config: this is the **same Key Vault secret the Python scraper already uses** for job-posting enrichment, already readable by the web app's managed identity via the existing `AddAzureKeyVault` wiring in `Program.cs` — **no new infra was needed** for this. Default model is `claude-sonnet-4-6` (configurable via an optional `anthropic-cover-letter-model` config key) — stronger than the scraper's enrichment-task model (`claude-haiku-4-5-20251001`), since free-form writing benefits more from a larger model than structured field extraction does.

Resume content is converted per extension: `.txt`/`.md`/`.html` → decoded UTF-8 text content block; `.pdf` → base64-encoded `document` content block; `.docx` never reaches this code (rejected earlier in the controller).

## Deliberate deviations from the original literal spec

- **`GET /cv/cover-letters` includes a `coverLetterName` field.** The literal example response didn't have one, but the only other display field (`coverLetterFileName`) is just `{guid}.txt` — unusable as a card title. The table already stores the name (used in the `POST /generate` response) for exactly this purpose.
- **`JobId` is stored but not returned** by `GET /cv/cover-letters`, matching the literal example exactly (only resume info is shown on cards).

## Infrastructure

`main.bicep` already had an unused `cover-letter` (singular) blob container from earlier scaffolding — renamed to `cover-letters` (plural) rather than adding a second container, the same resolution already applied to `resume`→`resumes` for the Resume feature. Note: Bicep renames deploy as a *new* resource rather than renaming in place, so the old empty `cover-letter` container is now orphaned (harmless — can be deleted manually via the Azure Portal/CLI if desired). A new `CoverLetters` table was added alongside the existing `Resumes`/`CustomerCriteria` tables. No new role assignments were needed — Storage Table Data Contributor, Storage Blob Data Contributor, and Storage Blob Delegator are all already scoped at the storage-account level from the Resume feature and automatically cover the new container/table.

## Endpoints (`CoverLetterController`, route `/cv`)

- **`POST /cv/generate`** `[Authorize]` — body `{ resumeId, jobBlobFileName, cvEnrichmentStyle }` (`cvEnrichmentStyle` one of `None`/`Prime`/`All`, case-insensitive). Validates the resume and job belong to the calling customer (`IResumeStorage.GetByIdAsync` / `IJobResultStorage.GetJobAsync` — the latter's customer-scoped blob path is itself the entire ownership check), rejects `.docx`, resolves style examples, calls Claude, uploads the result, writes the table row (rolling back the blob if the table write fails), and returns `{ resumeId, jobBlobFileName, coverLetterId, coverLetterName }`.
- **`GET /cv/cover-letters`** `[Authorize]` — the 3 most recent, each with a resolved resume name and a 1-hour SAS download URL (rows whose blob has gone missing are silently filtered out, same as the Resume feature).
- **`POST /cv/set-prime`** `[Authorize]` — body `{ coverLetterId }`, ownership-checked, toggles the Prime flag.

## Frontend

`CoverLetterGenerator` (`job-seeker.client/src/app/cover-letter-generator/`) is **not routed** — it's embedded directly in `dashboard.html` underneath the existing placeholder-cards section. It's self-contained (own `ngOnInit` fetch of jobs/resumes/cover-letters), with a job dropdown, a resume dropdown, a Bootstrap radio group for the style, and up to 3 cover-letter cards each with a download link and a star toggle for Prime.
